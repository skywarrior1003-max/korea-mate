## 1. 무엇을 고치나 · 영향을 알 수 없는 부분

- **결함(Production 에 있음, dcf874b4 이후):** 정상 온라인 저장에서 한 기록의 2번째 이후 사진이 서버에 올라가지 않고 그 기기 브라우저에만 남는다. 서버·다른 기기·Story·공유에는 기록마다 1장만 보인다.
- **영향 규모는 서버에서 셀 수 없다.** Production 의 추가 사진 0장(10-02 읽기)은 영향받은 사용자가 0명이라는 뜻이 아니다. 기기에만 남은 사진은 서버가 모른다. 브라우저 데이터를 지운 기기·다시 열지 않는 여행의 사진은 이 수정으로도 올라오지 않는다.
- **업로드만 고치면 안 되는 이유:** 다시 열 때 늦게 올라온 사진이 **이미 공개한 기록**에서 확인 없이 공개된다(Preview 재현). 그래서 공개 보호와 함께 나간다.

## 4. 배포와 배포 직후 확인 (실행 순서)

1. **배포 전 기록(읽기 전용)**
   - 추가 사진 수: `select count(*) from trip_moment_photos;`
   - 공개 기록 수: `select count(*) from trip_moments where is_public;`
   - 시험용 공개 여행 하나(운영자 소유)의 익명 공개 Story 사진 수: `GET /api/shared/<id>/story` → `memories[].photos.length` 합
2. **Pages 배포(이 브랜치).** 주소가 새 배포로 바뀌는 데 Preview 실측 11~16초 — 그동안 열린 탭은 옛 화면으로 동작한다(안전).
3. **배포 직후 5분 안에 확인:**
   - `GET /api/trip-moments?itinerary_id=<운영자 여행>`(로그인) 응답 머리글 `x-gkm-late-photo-guard: 1`
   - `POST /api/trip-moments/00000000-0000-4000-8000-000000000000/photos`(인증 없이) → 401 이고 같은 머리글 `1`
   - 1번의 익명 공개 Story 사진 수가 **그대로**
   - 운영자 시험 기록에 사진 3장 남기기 → 다른 기기(같은 계정)에서 3장 · 소유자 목록 `public_pending_photos` 없음
4. **중단 기준(하나라도 → §5-가 또는 §5-나):** 머리글이 없거나 `0` · 익명 공개 Story 사진 수가 소유자 확인 없이 늘었다 · `/photos` 5xx 가 평소보다 늘었다 · `select count(*), count(distinct storage_path) from trip_moment_photos` 두 값이 다르다(중복)
5. 이상이 없으면 24시간 동안 3번 확인을 하루 2회.

## 5. 되돌림 (위에서부터 먼저 쓴다)

### 가. 운영 정지 스위치 — 배포 없이, 공개 보호 유지
- 켜기: `insert into ai_ops_switches (ops_key, value_text) values ('moment_extra_photos','paused') on conflict (ops_key) do update set value_text='paused';`
- 효과(Preview 실측): 추가 사진 업로드만 멈춘다(목록 표시 `0`, `/photos` 503 PAUSED, 앱은 보내지도 않음). **첫 사진 저장·기록 열람·메모·공개 Story 는 그대로.**
- 사용자 영향: 새로 남긴 기록의 2번째 이후 사진은 그 기기에만 있다가, 해제한 뒤 그 기기에서 여행을 다시 열 때 올라간다(실측: 정지 중 서버 1장·기기 2장 → 해제 뒤 3장·0장). 거짓 "저장됨" 없음. 다른 기기에서는 해제 전까지 1장만 보인다.
- 해제: `delete from ai_ops_switches where ops_key='moment_extra_photos';`

### 나. 클라이언트만 옛 판으로 — 공개 보호 유지
- 미리 만들어 둘 것: master(`ecc5bf01`)의 `src` 로 빌드한 정적 파일 + 이 브랜치의 `functions` 를 한 배포로(빌드: 이 브랜치에서 `git checkout ecc5bf01 -- src` → `npm run build:static` → `git checkout HEAD -- src` → 그 `out` 을 이 브랜치 HEAD 에서 `wrangler pages deploy`).
- 효과(Preview 실측): 화면은 옛 동작(첫 사진만 저장), 서버의 공개 보호는 그대로(늦은 사진 주소 404·공개 Story 사진 수 그대로).
- 사용자 영향: 다시 수정 전처럼 2번째 이후 사진이 기기에 남는다. 이미 올라온 사진은 그대로 보호된다.

### 다. 최후 수단 — 공개 보호 없는 옛 서버(master 전체)로
- **위험(Preview 실측):** 이미 올라온 늦은 사진이 공개 기록에서 **바로** 익명에게 보인다(공개 Story 1→3장, 사진 주소 200).
- 반드시 되돌리기 **전에** `moment-extra-photos-rollback.sql` 을 순서대로:
  - **① 읽기** — "공개 기록인데 공개 동의 뒤에 올라온 추가 사진이 있는 기록" 목록과 장수. 0건이면 ②③ 없이 되돌려도 노출이 없다.
  - **② 숨기기** — 그 기록들을 비공개로 바꾸고 원래 공개 동의 시각·판본을 **결과로 돌려준다 — 이 결과를 파일로 보관한다.** 이 기록들은 **첫 사진과 메모까지 공개 Story 에서 빠진다**(늦은 사진만 골라 숨길 수단이 옛 서버에는 없다). 사용자 화면에는 "비공개" 로 보인다.
  - **③ 복원** — 공개 보호가 있는 배포(이 브랜치 또는 V2)를 다시 올린 **뒤에만** ② 의 보관 값으로 되돌린다. 동의 시각이 원래 값이라 늦은 사진은 계속 비공개로 남고, 첫 사진·메모는 다시 공개된다(Preview 실측: 공개 1장·늦은 사진 404). 옛 서버인 상태에서 ③ 을 하면 늦은 사진이 다시 노출된다.
- 새 화면이 열려 있던 탭은 옛 서버로 바뀌어도 추가 사진을 보내지 않는다(실측 0) — 되돌림 동안 새로 생기는 노출은 없고, 위험은 "이미 올라온 늦은 사진" 뿐이다.
