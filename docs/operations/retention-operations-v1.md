## 1. 자동 파기(DB) — 082 + 083

**083 활성화 관문(ROLLOUT-SAFETY-V1)** — 082 만 설치되면 첫 KST 03:27 부터 시행일·알림과 무관하게 파기한다(Staging 원장 1·2번이 알림 없이 삭제한 실례). 083 이 함수를 교체해 매 실행을 다음 순서로 거른다. 설정 행은 `public.retention_purge_settings`(단일 행).

| 실행 시 상태 | 원장 status | 삭제 | 알림 경로 호출 |
|---|---|---|---|
| 설정 행 없음(설치 직후·출시 전) | `inactive` | 0 | 없음(엔드포인트가 아직 없을 수 있음) |
| 활성화됨, KST 오늘 < 시행일 | `inactive` | 0 | probe 1회 |
| Vault 알림 URL·키 중 하나라도 비어 있음 | `blocked_no_alert` | 0 | 없음(보낼 곳이 없음) |
| 최근 36시간 안에 알림 경로 확인 없음 | `blocked_alert_unverified` | 0 | probe 1회(살아나면 다음 날 자동 재개) |
| 위 조건 모두 통과 | `ok` / `failed` | 규칙대로 / 전부 롤백 | 실패·월요일 점검 알림 + probe |

- **probe**: 알림 엔드포인트에 `kind=probe` — 메일을 보내지 않고 인증과 메일 설정 존재만 확인(200 ready / 503 not_configured / 401 키 불일치).
- **대조**: cron `gokoreamate-retention-alert-reconcile-v1`(매일 KST 03:57)이 pg_net 응답 코드를 원장 `alert_http_status`·`probe_http_status` 로 옮기고, probe 200 이면 `alert_verified_at` 을 갱신한다. pg_net 응답은 6시간만 남으므로 이 옮김이 영구 기록이다.
- **활성화**: `retention_alert_selftest()`(운영자에게 시험 메일 1통) → 응답이 202 일 때만 `retention_purge_activate(시행일)` 이 성공한다. 202 는 **발송 서비스가 수락**했다는 뜻까지이고, 운영자 수신은 사람이 메일함에서 확인한다.
- 원장 `alert`: `queued` = 요청을 대기열에 넣음(082 시절 `sent` 와 같은 뜻). 실제 결과는 `alert_http_status` — 202 발송 수락 / 502 발송 실패(사유: not_configured·provider_error·network_error) / 401 키 불일치 / 0 응답 없음.

## 2. 문의 보관 예외(진행 중 문의만)

- 관리자 API `PATCH /api/admin/contact-inquiries` 에 `retentionHold: { until, reason, by }` — 검토일은 오늘부터 1년 이내, 사유 5~500자, 책임자 필수. 해제는 `retentionHold: null`.
- 검토일이 지나면 예외가 끝나 다음 실행에서 일반 기준으로 파기된다. 계속 보관해야 하면 검토일 전에 새 사유·검토일로 갱신한다.

## 4. 이용자 요청(열람·정정·삭제)

법정 흐름: 요청을 받으면 **지체 없이** 확인해 필요한 조치를 하고, **요청을 받은 날부터 10일 이내** 결과를 알린다. 10일은 대기 기간이 아니라 통지 상한이다. 결과는 요청한 이메일로 보낸다.

- **문의 기록**: 요청 메일의 발신 주소가 문의 이메일과 같은지 확인(다르면 그 주소로 확인 메일 후 진행) → 이메일 + 대략의 접수일로 특정(이름만으로 찾지 않음) → 여러 건이면 목록을 보여 주고 확인 → DB 행 삭제(관리자 화면)와 메일함 사본 삭제 → 결과 회신.
- **신고 기록**: 대상·날짜·사유·메모 내용으로 하나로 특정될 때만 삭제. 특정할 수 없으면 삭제하지 않고 그 사실과 이유를 10일 이내에 알린다.
- 보관 목적이 없어진 기록(예: 스팸 문의)은 6개월을 기다리지 않고 삭제할 수 있다.
