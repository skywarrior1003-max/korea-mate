| 항목 | 값 |
|---|---|
| `document_title` | GoKoreaMate Product Constitution |
| `document_version` | **1.1** |
| `status` | **ACTIVE** — GoKoreaMate 제품 목적·사용자 흐름·기능 판단의 공식 최상위 SSOT v1.1 |
| `scope` | 제품 정체성 · 사용자 가치 · 기능 우선순위 · 공개/개인정보 · 바이럴 · 수익화 원칙 |

| `data_authority` | 데이터 · DB · readiness · provenance 세부는 `../architecture/gokoreamate-data-contract-v1.md`(v1.2 ACTIVE)가 **우선한다** |

| `conflict_rule` | 코드 · DB · 공식 SSOT와 이 문서가 충돌하면 **임의 진행하지 않고 중단·보고**한다 |
| `change_control` | 핵심 원칙 변경은 §20 변경 통제 절차와 **사용자 명시 승인**을 거친다. 변경 이력은 §20-2 |
| `last_change` | 2026-07-30 · v1.0 → v1.1 · §14-1 을 상업 표면 세 범위 정책으로 교체 |

**권한 관계**

| 문서 | 권한 |
|---|---|
| **Product Constitution** (이 문서) | 제품 목적 · 사용자 흐름 · 기능 판단 · 공개/개인정보 · 바이럴 · 수익화 |
| **Data Contract** | 데이터 · DB · readiness · provenance · identity · 병합·보강 |
| **Product Status** | **권한 없음.** 현재 구현 사실만 기록 |

**실제 코드·DB가 이 문서와 다르면 문서에 맞추지 말고 작업을 중단하고 차이를 보고한다.**

**이 문서에 쓰지 않는 것** 행 수 · 컬럼 수 · 파일 경로와 줄 번호 · 오류 코드 · 특정 migration 번호 · 특정 모델명. 이런 값은 운영만 해도 달라지므로, 최상위 원칙 문서에 넣으면 문서가 스스로 낡는다. 전부 Status 문서에 둔다.

## 0. 상태 표기 규칙

기능·자산을 서술할 때는 아래 표기를 쓴다. **구현되지 않은 것을 구현된 것처럼 쓰지 않는다.**

| 표기 | 의미 |
|---|---|
| `PRINCIPLE` | 구현 여부와 무관하게 지켜야 할 원칙 |
| `IMPLEMENTED` | 저장소·운영에서 실측 확인된 현재 기능 |
| `PARTIAL` | 일부만 구현. 나머지는 미구현 |
| `PLANNED` | 방향은 확정. 구현 없음 |
| `KNOWN_DEVIATION` | 원칙과 현재 코드가 다름을 알고 기록한 상태 |
| `UNKNOWN` | 확인되지 않았거나 미결정 |

**개별 기능의 현재 표기값은 이 문서가 아니라 Status 문서가 관리한다.** 이 문서는 표기 체계와 원칙만 정한다.

## 1. 제품의 존재 목적 · PRINCIPLE

GoKoreaMate는 **관광지 목록 사이트가 아니며, Google Maps·Naver Maps의 대체재도 아니다.**

GoKoreaMate는 사용자가 한국 여행을 다음과 같이 하도록 돕는다.

- 발견하고
- 저장하고
- 계획하고
- 실제로 경험하고
- 장소·사진·메모·스토리·일정을 추억으로 남기고
- 원하는 범위에서 공유하며
- 다른 여행자의 새로운 여행으로 이어지게 한다

목록의 크기가 아니라 **여행 한 번이 실제로 잘 되게 하는 것**이 제품의 일이다.

---

## 2. 장기 핵심 차별점 · PRINCIPLE

> **GoKoreaMate의 장기 핵심 차별점은 관광정보의 양 자체가 아니다.**
>
> 사용자의 추억 장소 · 개인 장소 · 사진 · 메모 · 스토리 · 여행 일정 · 복사와 반응 관계가 **사용자의 선택과 동의 아래** 계속 축적되고, 개인 지도 · 공개 발견 · 추천 · 공유 · 새 일정으로 다시 연결되면서 서비스 가치가 커지는 구조다.
>
> **공개 카탈로그 장소 데이터는 초기 발견과 일정 품질을 위한 기반 자산이다. 장기적인 핵심 자산은 사용자들이 만든 여행 기록과 그 관계다.**

이 차별점은 다음 다섯 가지를 동시에 지킬 때만 성립한다.

1. **축적과 공개를 구분한다.** 저장되는 것과 보이는 것은 다르다.
2. **개인 기록은 기본 비공개다.**
3. **공개는 사용자의 명시적 선택으로만 이뤄진다.**
4. **원천이 다른 데이터는 출처·신뢰 수준을 구분해 표시한다.**
5. **정확한 개인 위치와 사진을 자동 공개하지 않는다.**

이 다섯 가지를 어기면서 얻은 성장은 차별점이 아니라 부채다.

## 3. 핵심 사용자 순환 구조 · PRINCIPLE

```
Discover
  → Save
  → Plan
  → Experience
  → Record
  → Share
  → Others Discover and Copy
  → New Trips and Memories
  → Return and Contribute
      ↺ (루프 재시작)

        └─ (선택적 분기) Relevant Travel Purchases
```

**상업 구매는 루프의 필수 단계가 아니라 일정 확정 이후의 선택 가능한 결과다.** 사용자가 아무것도 구매하지 않아도 **발견 → 기록 → 공유 → 복사 → 새 여행** 루프는 완성돼야 한다. 구매가 있어야만 완결되는 설계는 이 원칙 위반이다.

**공유와 복사는 끝이 아니라 새로운 여행과 새로운 사용자 기록이 시작되는 연결점이다.** 공유 화면을 "읽고 끝나는 페이지"로 설계하면 루프가 끊긴다.

---

## 4. 누적되는 사용자 자산 · PRINCIPLE

제품이 축적을 목표로 하는 자산은 다음과 같다.

- 공개 카탈로그 장소 · 사용자가 등록한 장소
- 저장한 장소 · 일정에 추가한 장소 · 실제 방문한 장소
- 개인 일정 · 공개 일정 · 복사된 일정과 그 관계
- 사진 · 메모 · trip moments · Trip Cover · 여행 스토리
- 장소와 일정의 순서 · 날짜 · 동선 관계
- 저장 · 복사 · 도움됨 · 추천 · 반응 신호

**모든 데이터를 당장 공개하거나 추천에 사용한다는 의미가 아니다.** 저장 · 소유권 · 공개 동의 · 품질 검토 상태는 **각각 분리해서** 관리한다.

**축적의 최소 기준** 사용자의 핵심 여행 기록은 **브라우저 저장소에만 존재해서는 안 된다.** 브라우저를 지우면 사라지는 자산은 §2가 말하는 "계속 축적되는 자산"이 아니다. 각 자산의 현재 축적 수준은 Status 문서가 기록한다.

## 5. 사용자 자산 수명주기와 사용자 권리 · PRINCIPLE

- **핵심 여행 기록은 장기적으로 기기 변경·분실 후에도 복구 가능해야 한다** — `PRINCIPLE`
- 사용자는 자신의 기록을 **내보낼 수 있어야 한다**
- 사용자는 자신의 기록을 **삭제할 수 있어야 한다**
- **공개 동의 철회와 콘텐츠 삭제는 구분해 지원한다** — 공개를 멈추는 것과 데이터를 지우는 것은 다른 요구다
- 사용자 기록을 **플랫폼 소유물처럼 다루지 않는다**

**현재 소유권 구조에 대한 입장**

| 항목 | 판정 |
|---|---|
| 기기 간 복구 필요성 | `PRINCIPLE` |
| 복구 기능 도입 | `PLANNED` |
| 구현 방식(정식 계정 · 매직링크 · 패스키 · 복구키 등) | `UNKNOWN` — **정식 계정 도입 자체를 확정하지 않는다** |
| 기기 식별자 단독 소유권 | **과도기적 구현** — 장기 해답이 아니다 |

복구 방식이 정해지지 않았다는 것과 복구가 필요하다는 것은 다른 층위다. **필요성은 확정, 방식은 미정이다.** 이 구분을 흐리면 "계정을 만들 것이냐"라는 논쟁이 사용자 권리 보장을 막는다.

## 6. 개인정보와 공개 범위 · PRINCIPLE

- 개인 사진 **자동 공개 금지**
- 정확한 GPS **자동 공개 금지**
- 개인 장소 **자동 공개 금지**
- 공개 동의를 **철회할 수 있어야 한다**
- 공유 중단 · 비공개 전환이 **가능해야 한다**
- 공개 일정과 개인 편집본을 분리한다
- 소유권 없는 사용자는 수정할 수 없다
- **공개 조회를 위해 불필요한 로그인을 강제하지 않는다**
- 소유권 확인은 저장 · 복사 · 편집 · 복구에 사용한다

### 6-1. 개인 위치 공개 조건 — "서비스 내부"는 면제 사유가 아니다

| 대상 | 서비스 내부 상세 | 외부 OG · SNS |
|---|---|---|
| 공개 카탈로그 장소 | **표시 가능** | 정확 GPS·직접 지도 링크 기본 제외 |
| 사용자 개인 장소 | **해당 사용자의 공개 범위 설정을 따른다** | **정확한 개인 위치 기본 제외** |

> **서비스 내부라는 이유만으로 개인 위치 공개를 허용하지 않는다.**

공개 범위는 최소 3단계(숨김 기본 / 대략적 위치 / 사용자가 명시 허용한 정확 위치)로 구분하며, **기본값은 숨김**이다.

## 7. 지도 노출의 세 단계 · PRINCIPLE

"우리 지도에 나타난다"를 다음 세 단계로 구분한다. 단계를 건너뛰지 않는다.

| 단계 | 대상 | 조건 |
|---|---|---|
| **1. 개인 지도** | 본인의 장소·추억·일정 | 조건 없음 — 기본 상태 |
| **2. 공유 지도** | 사용자가 **공개한** 일정·스토리 | 사용자의 명시적 공개 선택 |
| **3. 공개 발견 지도** | 다른 사용자에게 **추천·노출**되는 장소·스토리 | 공개 선택 **+ 품질·중복·안전 검토 통과** |

> **핵심 원칙: 축적은 기본적으로 가능하게 하되, 공개는 사용자의 명시적 선택과 안전 검토를 거친다.**

**2단계와 3단계는 다르다.** 사용자가 일정을 공개했다는 사실이 그 안의 개인 장소를 발견 지도에 올려도 된다는 동의는 아니다.

## 8. 장소 용어와 원천 구분 · PRINCIPLE

**운영 장소 테이블에 들어갔다는 사실이 그 장소를 공식 기관 데이터로 만들지 않는다.** 다음 네 가지를 항상 구분한다.

| 용어 | 의미 |
|---|---|
| **공개 카탈로그 장소** | 발견·검색·일정 편성에 쓰이는 공개 운영 장소. **원천은 여러 종류다** |
| **공식 원천 장소** | 공공기관·공식 관광 API 등 공식 출처에서 온 장소 |
| **큐레이션·manual 장소** | 운영자가 직접 입력·정리한 장소 |
| **승인된 사용자 제보 장소** | 사용자가 제보하고 검토를 통과해 카탈로그에 반영된 장소 |

**"공식 장소"라는 말을 공개 카탈로그 전체를 가리키는 데 쓰지 않는다.**

**관리자 승인의 의미** 사용자 제보 → **검토 후 공개 카탈로그 반영**이다. 공식 기관 원천으로 바뀌는 것이 아니다. **승인 후에도 provenance는 사용자 제보로 보존되며, 공식 기관 원천으로 표시하지 않는다.**

---

## 9. 공식 데이터와 사용자 생성 데이터의 관계 · PRINCIPLE

- 공개 카탈로그 데이터는 **초기 발견·검색·일정 품질의 기반**이다
- 사용자 데이터는 **실제 경험·추억·새로운 장소 발견의 기반**이다
- 두 데이터를 **무조건 병합하지 않는다**
- 동일 장소 연결은 **identity 검증**을 거친다
- **개인 장소는 카탈로그 장소로 자동 승격하지 않는다**
- 사용자 제보 장소는 **소유자 개인 사용 상태와 공개 검토 상태를 구분**한다
- **provenance와 공개 상태를 보존**한다
- **사용자가 만든 기록을 공식 기관 설명처럼 표시하지 않는다**

---

## 10. 공개 사용자 콘텐츠 안전 원칙 · PRINCIPLE

공개된 사용자 장소·사진·메모·스토리는 핵심 자산인 만큼 다음을 갖춘다. **법률 약관이 아니라 제품 원칙 수준의 규정이다.**

- **스팸 · 중복 · 위험 위치 검토** — 공개 발견 단계 진입 전 필수
- **개인정보 침해 신고** 경로
- **저작권 · 초상권 신고** 경로
- **공개 철회** — 사용자가 언제든 공개를 되돌릴 수 있다
- **신고·운영 검토에 따른 숨김 또는 삭제**
- **사용자 콘텐츠를 공개 동의 범위를 넘어 재사용하지 않는다**
- **출처와 작성 주체를 표시한다**
- **공식 기관 정보처럼 오인시키지 않는다**

신고 경로 없이 사용자 콘텐츠를 공개 발견 지도에 올리지 않는다.

---

## 11. 일정 품질 원칙 · PRINCIPLE

**일정 품질 우선순위**

```
도착 → 출발 → 고정 행사 → 사용자가 직접 선택한 장소 → 사용자 취향 → 가까운 장소
```

- 사용자가 **먼저 장소를 고르고** 시스템이 일정을 구성한다
- **Add to Itinerary가 일정 입력의 중심**이다
- Like · Helpful · 반응은 **신호이지 강제 일정 입력이 아니다**
- **사용자가 선택한 장소를 제휴상품이나 광고보다 우선한다**
- 하루 단위 지역 묶기와 이동 순서 품질을 중시한다
- 실제 이동은 **외부 지도 앱으로 연결**한다
- **GoKoreaMate는 실시간 내비게이션을 직접 만들지 않는다**

---

## 12. 추천 원칙 · PRINCIPLE

**추천은 단순 조회 수나 광고비로 결정하지 않는다.**

**추천 신호 후보** — 사용자 저장 · 일정 포함 · 실제 방문 기록 · 일정 복사 · Helpful · 공개 추억 · 비슷한 여행자가 추가한 장소 · 같은 일정에서 함께 방문된 장소 · 계절·기간·동행 유형 · 거리와 일정 맥락 · 장소 신뢰도와 readiness.

**신호를 사용하기 전에 반드시 검토할 것**

- 개인정보
- 조작과 스팸
- 편향
- 신규 장소 불이익
- 공개 카탈로그 정보와 사용자 의견의 구분
- 설명 가능성
- 사용자가 추천을 끄거나 조정할 수 있는지

**추천이 사용자 기록을 신호로 쓴다는 것은 그 기록이 플랫폼 자산이 된다는 뜻이 아니다.** §5의 내보내기·삭제·공개 철회 권리는 추천 도입 이후에도 그대로 유지된다.

## 13. 바이럴 원칙 · PRINCIPLE

**바이럴의 중심은 목적지 홍보 이미지가 아니라 여행자가 자신의 여행을 보여주는 것이다.**

**공유 자산 우선순위**

1. 사용자가 **명시적으로 선택한** 개인 여행·추억 사진
2. 공개 허용된 Trip Cover 또는 moment
3. 일정 경로 · 날짜 · 장소 요약
4. **권리가 확인된** 장소 이미지
5. 도시 · 테마 fallback

**관광지·맛집 이미지는 주인공이 아니라 사용자 사진이 없을 때의 대체재다.**

공유 화면과 이미지에는 **필요 최소한의 정보만** 포함한다. SNS·OG 공유는 사용자의 추억과 일정 맥락을 보여주되 민감한 위치와 사적인 정보는 보호한다.

## 14. 수익화 원칙 · PRINCIPLE

**수익화 후보** — 숙박 · 액티비티·체험 · eSIM · 교통 · 입장권 · 여행 관련 상품 · 광고.

**고정 원칙**

- **스케줄러는 provider ID · offer ID · commission · commercial priority 등 상업 문맥 자체를 입력받지 않는다**
- **스케줄러는 비상업적 일정만 확정한다**
- **상품 연결은 일정이 확정된 뒤 추천·렌더링 계층에서 수행한다**
- 상업 정보는 **명확하게 구분해 표시**한다
- 특정 공급자를 애플리케이션 로직에 **하드코딩하지 않는다**
- eSIM 카테고리 방향은 채택됐으나 **공급자는 미확정**
- 신뢰 · 커버리지 · 수익성 · 취소·환불 · 다국어 · 추적 정확성 · 운영 비용을 함께 평가한다
- **제품 신뢰보다 단기 수익을 우선하지 않는다**

"장소 순서만 바꾸지 않으면 된다"가 아니다. **상업 문맥이 스케줄러 입력에 들어가는 순간 이미 원칙 위반이다.**

### 14-1. 상업 표면의 세 범위 · PRINCIPLE

상업 노출은 **여행자 선택과 일정 품질에 미치는 영향**에 따라 세 범위로 나누며, 각 범위에 독립적인 정책과 게이트를 적용한다. 하나의 게이트로 묶지 않는다.

> **파일명·컴포넌트명이 아니라 실제 사용자 표면과 데이터 흐름을 기준으로 판정한다. 동일한 컴포넌트도 사용 문맥이 다르면 다른 범위로 분류할 수 있다.**

#### A. Trip-Flow Commerce — 기본 비활성

장소 발견부터 일정 사용·공유까지의 여행 흐름에는 상업 문맥이 들어가지 않는다.

**대상 표면** 장소 발견과 검색 · 장소 카드와 장소 상세 · 저장과 일정 담기 · 일정 생성 · 일정 항목 내부 · 공유 일정 · 복사된 일정 · **여행계획 전환 흐름에 직접 붙은 사전 판매 CTA**.

**대상 객체** 장소 선택 객체 · Cart · Saved · 스케줄러 후보 · 스케줄러 입력 · plan API 요청 payload · 공유·복사 일정의 사용자 데이터.

**금지 사항**

- 상업 URL · 공급자 · 수수료 · 오퍼 · 상업 우선순위를 대상 객체에 넣지 않는다
- 장소 선택 · 일정 생성 · 일정 항목 안에 예약·구매 CTA를 표시하지 않는다
- 공유·복사 일정에 상업 링크를 자동 포함하지 않는다
- 상업정보가 장소 선택 · 일정 순서 · 점수 · 추천 결과에 영향을 주지 않는다

**DB의 제휴 원본과 공급자 설정은 삭제하지 않는다.** 금지하는 것은 원본 보관이 아니라 **Trip-Flow 경로로의 유입과 표시**다.

#### B. Post-Plan Commerce — 기본 비활성, 정상화 후 활성 가능

**비상업적 일정이 확정된 뒤**, 일정 데이터와 분리된 별도 영역에서만 상품을 연결할 수 있다.

확정된 도시 · 날짜 · 도착시간 · 여행기간 문맥을 읽을 수 있으나, **일정의 장소 선택 · 순서 · 점수에 어떤 방식으로도 되먹임하지 않는다.**

**활성화 전 필수 조건**

1. 스케줄러 입력과 완전 분리
2. provider-neutral recommendation adapter
3. 공급자명을 컴포넌트 로직에 직접 고정하지 않음
4. 카테고리별 공급자 비교와 사용자 승인
5. **화면에 보이는** `Sponsored` 또는 `Affiliate link` 표시
6. `rel="sponsored"` 만으로 가시적 고지를 대체하지 않음
7. 사용자가 선택한 경우에만 외부 상품 페이지로 이동
8. 취소 · 환불 · 다국어 · 추적 정확성 · 운영비 검토
9. 회귀 및 수익 추적 QA
10. 사용자 명시 승인

코드와 기존 추적 URL은 보존할 수 있으나, **조건 충족 전에는 운영 렌더를 활성화하지 않는다.**

#### C. Editorial Content Affiliate — 명시적으로 승인된 표면에서만 활성 가능

일정 흐름 밖의 편집 콘텐츠는 Trip-Flow와 **완전히 분리된 경우에 한해** 제휴 링크를 포함할 수 있다.

**허용 후보** 도시 소개와 여행 준비 콘텐츠 · 편집 블로그 · 일반 Survival Guide.

**필수 조건**

- 일정 · Cart · Saved · 스케줄러 · 공유 일정 · 사용자 기록과 **완전 분리**
- CTA 인접 위치 또는 콘텐츠 본문에 **사용자가 볼 수 있는 제휴 고지**
- 링크와 공급자를 **중앙 설정에서 관리**
- 공급자명을 개별 컴포넌트에 직접 하드코딩하지 않음
- 수수료나 광고비가 **편집 추천 순서를 바꾸지 않음**
- 공유·복사 일정에는 노출하지 않음
- 사용자 생성 콘텐츠에 자동 삽입하지 않음
- 개인정보나 개인 여행 문맥으로 자동 타기팅하지 않음
- **기존 링크 유지와 신규 공급자·표면 확장은 별도 결정으로 취급**

> **Editorial Content Affiliate 를 모든 콘텐츠에 전역 자동 활성화하지 않는다.**
>
> 운영 허용 표면은 **명시적인 분류 또는 allowlist** 를 가져야 한다. **분류되지 않은 신규 표면은 자동으로 Trip-Flow Commerce 로 판정하여 비활성화한다.**

**동일 컴포넌트의 문맥별 예**

| 사용 문맥 | 범위 |
|---|---|
| 도시 랜딩의 준비물 안내 섹션 | Editorial Content Affiliate 후보 |
| 공유 일정 화면의 **같은** 섹션 | **Trip-Flow Commerce** |

현재 가시적 고지나 중앙 설정 요건을 충족하지 못한 표면은 **기존 링크가 있더라도 정상화 전까지 허용 표면으로 확정하지 않는다.**

#### 공통 원칙

- **범위가 불분명한 표면은 Trip-Flow Commerce 로 분류한다.** 안전한 쪽으로 기운다
- 설정 또는 명시적 표면 분류가 없으면 **자동 활성화하지 않는다**
- **eSIM 등 카테고리 방향 채택과 특정 공급자 확정은 다른 결정이다**
- **기존 수익이 있다는 이유로 일정 품질 원칙을 완화하지 않는다**
- 제품 신뢰보다 단기 수익을 우선하지 않는다
- 이 정책의 변경은 §20 변경 통제와 **사용자 명시 승인**을 거친다

현재 코드의 편차와 그 근거는 Status 문서의 `KNOWN_DEVIATION` 항목에 있다.

## 15. 기능 우선순위 판단 기준 · PRINCIPLE

모든 신규 기능은 아래 중 **최소 하나를 분명히 강화**해야 한다.

1. 더 쉽게 장소를 발견한다
2. 더 쉽게 저장한다
3. 더 좋은 일정을 만든다
4. 여행 중 실제 사용성을 높인다
5. 더 쉽게 추억을 기록한다
6. 더 안전하게 공유한다
7. 다른 사용자가 발견·복사·활용하게 한다
8. 사용자 기록이 지도와 추천에 가치 있게 연결된다
9. 사용자가 다시 돌아오게 한다
10. 신뢰를 해치지 않고 수익으로 연결한다
11. **핵심 사용자 흐름을 보호하는 보안·운영 안정성을 높인다**
12. **데이터 손실 · 권한 오남용 · 개인정보 위험을 제거한다**
13. **장기 사용자 자산 관계를 보존한다**

어느 항목도 강화하지 않는 기능은 우선순위를 낮춘다. "데이터 수만 늘리고 위 어느 것과도 연결되지 않는 작업"이 여기에 해당한다.

> **사용자 화면을 직접 강화하지 않더라도 핵심 흐름을 보호하는 필수 보안·인프라 작업은 낮은 우선순위로 처리하지 않는다.** 11~13은 화면에 보이지 않는다는 이유로 밀리기 쉬우므로 명시적으로 기준에 넣는다.

## 16. 만들지 않을 것 · PRINCIPLE

- 단순 관광지 **수량 경쟁**
- Google Maps · Naver Maps **대체**
- 자체 **실시간 내비게이션**
- 개인 사진 · 정확한 위치 **자동 공개**
- 광고·제휴상품이 **일정 품질에 개입**하는 구조
- 서로 다른 원천의 데이터를 **구분 없이 노출**
- 공개 관광정보 열람을 위한 **불필요한 로그인 강제**
- 데이터 수만 늘리고 저장·일정·추억·공유와 **연결하지 않는 작업**
- 검토되지 않은 사용자 장소를 **공식 기관 정보처럼 노출**
- 단기 기능을 위해 **장기 사용자 자산 관계를 손실**하는 설계
- 사용자 기록을 **플랫폼 소유물처럼 다루는** 설계

## 17. 설계·개발 의사결정 절차 · PRINCIPLE

**역할로 정의한다. 특정 모델·도구 이름을 이 문서에 넣지 않는다.** 모델이 바뀌어도 제품 원칙은 바뀌지 않아야 한다.

| 역할 | 책임 |
|---|---|
| **저장소·DB 사실 조사 및 구현 담당** | 실제 코드·DB 실측, 설계안 작성, 구현, 자동검증 |
| **독립 제품·아키텍처 검증 담당** | 반대 관점 검증, 위험·누락 지적 |
| **사용자** | 최종 결정권자 |

**절차**

1. 제품 목표와 관련 원칙 확인
2. 실제 저장소·DB 사실 조사
3. 사실 · 추론 · 결정 · 미확인 사항 분리
4. 기술 설계안 작성
5. **독립 검증** — 반대 관점에서 검토
6. 사용자에게 권장안 · 위험 · 불확실성 보고
7. 구현
8. 자동검증
9. 운영 적용 전 **사용자 명시 승인**
10. 배포 후 QA

> **어떤 도구의 기억도 공식 SSOT와 실제 저장소보다 우선하지 않는다.**

현재 각 역할을 누가 수행하는지는 운영 규칙·인수인계 문서에 기록하며, 이 문서에는 넣지 않는다.

**다음 중 하나라도 해당하면 구현을 중단하고 사용자 결정을 받는다.**

- 제품 영향에 **`약화`**가 있고 명시적 사유·승인이 없음
- 미확인 사항이 **보안 · 개인정보 · 데이터 손실 · 핵심 데이터 모델 · 운영 복구**에 실질적 영향을 줄 수 있음
- **핵심 Product Constitution 원칙을 약화**함
- **되돌리기 어려운 운영 변경**의 영향이 확인되지 않음

**위에 해당하지 않는 미확인 사항은 blocker가 아니다.** `UNKNOWN`과 가정을 기록하고 **되돌릴 수 있는 범위에서 진행할 수 있다.** 모든 `확인 필요`가 작업을 멈추게 하면 아무것도 진행되지 않는다.

## 20. 변경 통제 · PRINCIPLE

Product Constitution을 변경하려면 다음을 기록해야 한다.

- 변경 이유
- 사용자 가치
- 기존 원칙과의 충돌
- 영향을 받는 기능 · 데이터 · 문서
- 개인정보 · 수익화 영향
- 권장안
- **사용자 명시 승인**

> **어떤 도구도 임의로 핵심 원칙을 변경해서는 안 된다.**

### 20-1. Status 문서의 갱신은 다르다

**Status 문서는 위 변경 승인 절차 없이 갱신할 수 있다.** 실측값이 바뀌면 바로 고친다. 그것이 두 문서를 나눈 이유다.

다만 **승인 절차가 없다는 것이 증거 없이 고쳐도 된다는 뜻은 아니다.**

- Status 갱신에는 **실제 저장소 · 운영 DB · 배포 결과 등 확인 가능한 증거가 필수**다
- 저장소 사실에는 `verified_commit`, DB 사실에는 `verified_db_date`를 기록한다
- **`FACT` · `INFERENCE` · `UNKNOWN`을 구분**하며, 확인하지 않은 내용을 `IMPLEMENTED`로 바꾸지 않는다
- **Status는 사실을 기록할 뿐, 제품 원칙이나 제품 결정을 만들거나 바꿀 수 없다**

Status에 무언가를 적었다는 사실은 그것이 원칙이 됐다는 뜻이 아니다. 원칙을 바꾸려면 §20 본문의 절차를 거쳐야 한다.

### 20-2. 변경 이력

#### v1.0 → v1.1 · 2026-07-30 · §14-1 교체

**승인 주체** 사용자 명시 승인

**변경 대상** §14-1 「`HARD_GATE` — 상업 활성화 선행 조건 (기술 중립)」 → 「상업 표면의 세 범위」

**변경 이유**

- 기존 단일 HARD_GATE 가 **일정 흐름 오염**과 **일정 밖 편집 콘텐츠**를 구분하지 못했다. 게이트가 걸린 이유는 "스케줄러 내부의 상업 주입 경로"였는데, 금지 목록의 "사용자에게 상업 카드·상품 노출 활성화"가 주어를 잃어 스케줄러와 무관한 표면까지 포함됐다
- 그 결과 일정 품질에 아무 영향이 없는 콘텐츠 수익 표면까지 **과잉 차단**할 위험이 있었다
- 실제 운영 표면을 전수 조사한 결과 Trip-Flow · Post-Plan · Editorial Content 의 **제품 위험 수준이 서로 다르다**는 것이 확인됐다
- 기존 문구의 기술 중립화가 **범위 중립까지 함께 만들어 버린 것**이 직접 원인이다

**유지한 핵심 원칙** 스케줄러 상업 문맥 차단 · 일정 품질과 상업정보 분리 · 일정 확정 후 별도 상품 연결 · 공급자 하드코딩 금지 · 가시적 제휴 고지 · 제품 신뢰 우선.

**영향**

| 항목 | 영향 |
|---|---|
| 사용자 가치 | 장소 선택·일정 경로에서 상업 CTA 가 사라져 판단이 깨끗해진다 |
| 신뢰 | 고지 없는 판매 링크가 장소 카드에서 제거된다 |
| 수익 | Trip-Flow·Post-Plan 차단으로 **단기 손실 발생**. 실제 추적 링크가 존재하므로 손실을 0 으로 표현하지 않는다. Editorial Content 는 유지된다 |
| 개인정보 | 변화 없음. Editorial Content 에 개인 여행 문맥 타기팅 금지를 명문화 |
| 되돌리기 | 이 문서 commit revert 로 v1.0 문구 복원 가능 |

**알려진 위험** ①세 범위 분할로 판정 경계가 생긴다 → "불분명하면 Trip-Flow" 규칙으로 보완 ②Editorial Content 허용이 무분별 확장 유인이 된다 → 명시적 allowlist 요구와 "기존 유지와 신규 확장은 다른 결정" 조항으로 보완.

**이번 변경에 포함하지 않은 것** 코드 구현 · 게이트 신설 · 제휴 링크 활성화·비활성화 · 공급자 선정 · DB 변경. **문서 변경만으로는 코드가 정책을 준수하게 되지 않는다.** 현재 편차는 Status 문서가 기록한다.

## 21. 문서 권한 구조 · PRINCIPLE

세 문서의 권한은 다음과 같이 분리돼 있다. **이 구조는 세 문서에 모순 없이 나타나야 한다.**

| 문서 | 상태 | 권한 |
|---|---|---|
| **Product Constitution v1.0** | `ACTIVE` | 제품 목적 · 사용자 흐름 · 기능 판단 · 공개/개인정보 · 바이럴 · 수익화 |
| **Data Contract v1.2** | `ACTIVE` | 데이터 · DB · readiness · provenance · identity · 병합·보강 |
| **Product Status v1.0** | `VERIFIED_SNAPSHOT` | **`authority: NONE`** — 현재 구현 사실만 기록 |

**유지 규칙**

1. **제품 판단 기준 목록은 이 문서 한 곳에서만 관리한다.** Data Contract는 제품 방향을 이 문서 참조로만 두고 상세 목록을 중복 보유하지 않는다.
2. Data Contract는 이 문서의 제품 원칙을 **데이터·DB 구조로 구현**한다. 데이터 설계가 이 문서와 충돌하면 임의 진행하지 않고 중단·보고한다.
3. **Product Status는 활성화 전환 대상이 아니다.** 항상 `authority: NONE`이며 원칙이나 제품 결정을 만들거나 바꿀 수 없다.
4. **세 문서의 상호 링크를 유효하게 유지한다.**
5. **권한 관계를 바꾸는 변경은 세 문서를 같은 commit에서 동기화한다.** 한 문서만 먼저 바꾸면 어느 쪽이 유효한지 판단할 수 없는 기간이 생긴다.
